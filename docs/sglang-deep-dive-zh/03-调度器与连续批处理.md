# 03 · Scheduler 调度器与连续批处理

> `managers/scheduler.py` 是整个 SGLang 的「心脏」。本篇解析它的事件循环、拼批算法、
> 以及 overlap 模式如何让 CPU 与 GPU 同时不闲着。

---

## 1. Scheduler 是什么

`Scheduler` 类(`scheduler.py:359`)是一个**单线程事件循环驱动的状态机**,每个 TP rank 一个实例。它同时管理:

- 三个队列:`waiting_queue`(等 prefill)、`running_batch`(正在 decode)、以及临时拼出的 prefill 批;
- 内存与缓存:`token_to_kv_pool_allocator`(KV 槽位分配器)、`tree_cache`(RadixCache);
- 执行后端:`tp_worker`(封装 `ModelRunner`);
- 输出管道:把结果发给 detokenizer。

**rank0 是「收发者」而非唯一决策者**:它负责收请求(ZMQ),并在 `recv_requests()` 里把**原始请求对象**用 `broadcast_pyobj` 广播给其它 rank(走 CPU 进程组;DP attention 下先拆 work/control 请求,再经 attn_tp 组转发)。拿到同样的请求输入后,**每个 rank 独立跑同一套拼批逻辑**,产出一致的批。这种「广播输入、确定性重放决策」的设计要求所有 rank 的调度状态严格同步——任何 rank 间状态分叉都会导致批不一致,进而集合通信死锁(分布式调试的头号怀疑对象)。

## 2. 事件循环:normal 与 overlap

### 2.1 event_loop_normal —— 理解基线

```1632:1663:python/sglang/srt/managers/scheduler.py
    def event_loop_normal(self):
        """A normal scheduler loop."""
        while True:
            if self.gracefully_exit:
                break

            # Receive requests
            recv_reqs = self.request_receiver.recv_requests()
            self.process_input_requests(recv_reqs)
            if self._engine_paused:
                continue

            # Get the next batch to run
            plan = self.get_next_batch_to_run(
                running_batch=self.running_batch, last_batch=self.last_batch
            )
            self.running_batch = plan.running_batch
            batch = plan.batch_to_run

            # Launch the current batch
            if batch:
                result = self.run_batch(batch)
                self.process_batch_result(batch, result)
            else:
                # When the server is idle, do self-check and re-init some states.
                self.on_idle()

            self.last_batch = batch
```

每圈四步:**收请求 → 拼批 → 跑批 → 处理结果**。简单、同步、易调试。问题是:GPU 在跑的时候 CPU 闲着,CPU 在拼批的时候 GPU 闲着。

### 2.2 event_loop_overlap —— 生产默认

`event_loop_overlap`(`scheduler.py:1666`)把「处理上一批结果」与「发射本批前向」交错:

```1677:1734:python/sglang/srt/managers/scheduler.py
        while True:
            ...
            # Receive requests
            recv_reqs = self.request_receiver.recv_requests()
            self.process_input_requests(recv_reqs)
            ...
            # Get the next batch to run
            plan = self.get_next_batch_to_run(...)
            ...
            # Launch the current batch
            if batch:
                batch_result = self.run_batch(batch)
                ...
                self.result_queue.append((batch.copy(), batch_result))
            else:
                batch_result = None

            # Process the last batch
            if self.last_batch:
                if not disable_overlap_for_batch:
                    pop_and_process()
            ...
```

核心思想:**第 N 圈的 GPU 前向与第 N-1 圈结果的 CPU 后处理并行**。为此:

- 结果进 `result_queue`,延后一拍处理;
- `batch.copy()` 保存快照,防止后续修改污染;
- 某些场景(连续两个 prefill 批)会 `disable_overlap`,优先保首个请求的 TTFT。

> 代价:调度器看到的系统状态「滞后一拍」。很多边界条件(内存检查、grammar 状态)都要考虑这一点。

## 3. 拼批:get_next_batch_to_run

`get_next_batch_to_run`(`scheduler.py:2872`)每圈回答一个问题:**下一步跑什么?**

决策顺序:

1. **尝试组 prefill 批**:`get_new_batch_prefill(running_batch)` —— 从 `waiting_queue` 里挑请求。若组出非空批,优先跑它(可能混合 decode 请求形成 MIXED 批)。
2. **否则跑 decode**:从 `running_batch` 里剔除已完成的,剩余的组 DECODE 批。
3. 都没有 → 返回空,循环进入 `on_idle()`(清缓存、自检、睡眠)。

### 3.1 get_new_batch_prefill:等待队列准入

`get_new_batch_prefill`(`scheduler.py:3014`)流程:

1. **排序等待队列**:按 `--schedule-policy`:
   - `lpm`(longest prefix match,默认):按 RadixCache 命中长度降序,命中多的先跑,最大化缓存收益;
   - `fcfs` / `random` / `dfs-weight` 等备选。
2. **逐请求询问 PrefillAdder**:「还能不能再加一个?」直到预算耗尽。
3. 处理 chunked prefill:一个超长请求可以只算一部分(`chunked_prefill_size`),剩余部分下圈继续(该请求成为 `chunked_req`)。

### 3.2 PrefillAdder:预算守门员

`PrefillAdder`(`schedule_policy.py:444`)是准入的核心。它持有几类预算,`add_one_req` 对每个候选请求逐项检查,任一项不足就停止准入。

**第一类:token 空间预算(动态属性,不是静态计数器)**

`rem_total_tokens` 和 `cur_rem_tokens` 是 `@property`,每次访问都重新计算:

```586:590:python/sglang/srt/managers/schedule_policy.py
            available_and_evictable = (
                self.token_to_kv_pool_allocator.available_size()
                + self.tree_cache.evictable_size()
            )
        return available_and_evictable - self.rem_total_token_offset
```

三个组成部分要分清:

- `available_size()`:分配器手里**当前空闲**的槽位;
- `evictable_size()`:RadixCache 里**可驱逐**的槽位(`lock_ref == 0` 的部分)——注意这部分虽然被缓存占着,但随时能腾出来,所以计入可用余量。被活跃请求锁住(`protected_size`)的部分**不算**;
- `rem_total_token_offset`:本轮已承诺出去的额度(见下)。

**第二类:输入长度预算**

- `rem_input_tokens`:本批总共还能吃多少新 token(初值来自 `chunked_prefill_size`,并先扣掉混批中 decode 请求占的 token);
- `rem_chunk_tokens`:单个请求本次最多切多少(`None` 表示 chunked prefill 被禁用,请求必须一次算完)。

**第三类:请求数预算** —— `max_running_requests`、`prefill_max_requests`、`max_prefill_bs`。

**第四类:特殊模型预算** —— `rem_swa_tokens`(滑动窗口模型的窗口池)、`rem_mamba_slots`(混合线性注意力模型的状态槽,与 KV 共享字节缓冲时必须单独把关,否则会过度承诺)。

#### new_token_ratio:为「还没生成的输出」预留空间

这是 SGLang 调度里最不直观、也最关键的一个机制。问题是:一个请求 prefill 时占 1000 token 的 KV,但它接下来还要生成最多 `max_new_tokens` 个 token,每个都要新槽位。如果准入时只看当前占用,decode 阶段必然撞墙。

SGLang 的解法是**按比例悲观预留**:

```559:566:python/sglang/srt/managers/schedule_policy.py
    def _get_running_request_total_token_offset(self, req: Req) -> int:
        return (
            min(
                (req.sampling_params.max_new_tokens - len(req.output_ids)),
                CLIP_MAX_NEW_TOKENS,
            )
            * self.new_token_ratio
        )
```

对每个**正在运行**的请求,按「还剩多少 token 要生成」× `new_token_ratio` 预扣额度,累加进 `rem_total_token_offset`。所以:

- `new_token_ratio = 1.0` → 完全悲观:假设每个请求都会生成到 `max_new_tokens`,准入极保守,几乎不会 retract 但 GPU 利用率低;
- `new_token_ratio → 0` → 完全乐观:假设请求马上就结束,激进准入,吞吐高但可能频繁 retract。

`CLIP_MAX_NEW_TOKENS` 的作用是防止用户传一个巨大的 `max_new_tokens`(比如 32768)把预留额度撑爆,导致谁都进不来。

#### 反馈环:retract 与 new_token_ratio 的博弈

`new_token_ratio` 不是固定值,而是由 `NewTokenRatioTracker`(`scheduler_components/new_token_ratio_tracker.py`)动态调节的**闭环控制器**:

```34:51:python/sglang/srt/managers/scheduler_components/new_token_ratio_tracker.py
    def decay_step(self) -> None:
        self.current = max(self.current - self.decay, self.min)

    def reset(self) -> None:
        self.current = self.init

    @staticmethod
    def estimate_new_token_ratio_after_retract(reqs: Sequence[Req]) -> float:
        total_decoded_tokens = sum(len(r.output_ids) for r in reqs)
        total_max_new_tokens = sum(r.sampling_params.max_new_tokens for r in reqs)

        new_estimate_ratio = (
            total_decoded_tokens + envs.SGLANG_RETRACT_DECODE_STEPS.get() * len(reqs)
        ) / (
            total_max_new_tokens + 1
        )  # avoid zero division
```

闭环逻辑:

1. **平稳期**:每轮 decode 若内存充裕,调 `decay_step()` 把 ratio 往下降(逐步变乐观),直到 `min`——系统自动试探更高的并发;
2. **撞墙时**:一旦触发 retract,立刻用 `estimate_new_token_ratio_after_retract` 根据实际观测(已生成/上限的比值)把 ratio **跳回高位**,变回保守;
3. 初值由 `init_new_token_ratio × --schedule-conservativeness` 决定 —— 这就是那个调优参数的真实作用点:**它不直接限制并发,而是设定这套悲观预留的起点**。

> 调优提示:如果日志里频繁出现 retract 警告,说明 ratio 衰减得太快或负载的输出长度方差太大,可以调大 `--schedule-conservativeness`;反之如果 GPU 利用率上不去且从不 retract,可以调小它。

**总结**:准入预算是吞吐/延迟权衡的总开关,而 `new_token_ratio` 是这个开关的自适应部分——预算大→吞吐高但单请求排队久、retract 风险高;预算小→TTFT 好但 GPU 利用率低。

## 4. 连续批处理(Continuous Batching)本质

传统 static batching 必须等整批都结束。SGLang 的连续批处理体现在三点:

1. **随时加入**:任何一圈,waiting_queue 的请求都可能在 prefill 批中启动;
2. **随时离开**:任何请求在 `process_batch_result` 中完成即被 `filter_batch` 剔除,槽位立刻回收;
3. **prefill/decode 混合**:MIXED 模式让新请求的 prefill 与老请求的 decode 在同一前向中执行(chunked prefill 的核心收益)。

配合 RadixCache:新请求命中的前缀**不占新槽位、不重复计算**,等效于「免费延长」了它的历史。

## 5. 内存压力处理

每圈拼批前/中,scheduler 会评估 KV 余量,三道防线依次收紧:

- `PrefillAdder` 准入时只算「可驱逐」余量(树里未被锁定的部分);
- 真到分配时,`alloc_token_slots` 触发 `evict_from_tree_cache`,从 RadixCache 逐出 LRU 叶子(见文档 04);
- decode 阶段若 `check_decode_mem()` 发现余量不够,`update_running_batch` 会触发 **retract**(`batch.retract_decode`):按排序选出最「不值得留」的请求,释放其 KV(**不入树**,因为要立刻腾空间),重新塞回 waiting_queue(`is_retracted=True`)。由于 KV 没进树,这些请求下次 prefill 基本要重算,代价最大,属最后手段;若连最后一个请求都放不下,会优雅 abort 而不是让 scheduler 崩掉。

## 8. 本篇要点回顾

1. Scheduler 是单线程事件循环:收请求 → 拼批 → 跑批 → 处理结果,周而复始。
2. overlap 模式用一拍延迟换取 CPU/GPU 全并行,是生产默认。
3. 拼批 = 等待队列排序 + `PrefillAdder` 预算准入 + chunked prefill 切片。
4. 连续批处理:请求随时进出、prefill/decode 可混批。
5. 内存不足时的防线顺序:驱逐缓存 → 收紧准入 → retract。
