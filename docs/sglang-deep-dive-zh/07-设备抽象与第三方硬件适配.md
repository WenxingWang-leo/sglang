# 07 · 设备抽象层与第三方硬件适配(重点)

> 本篇是第三方设备适配的「总纲」:讲透 `platforms/` 抽象层、`hardware_backend/` 实现层、
> 插件式接入机制(setuptools entry-points)、以及内核分发的三条路径,
> 最后给出一份端到端的适配路线图。建议反复精读,并配合官方文档
> `docs_new/docs/hardware-platforms/plugin.mdx` 阅读。

---

## 1. 适配的全景:你要填哪些「格子」

把一个新芯片接入 SGLang,本质是填满下面这张表:

| 格子 | 抽象入口 | 说明 |
|---|---|---|
| ① 平台身份与设备操作 | `SRTPlatform`(继承 `DeviceMixin`) | 显存查询、同步、设备枚举等 |
| ② 插件注册 | setuptools entry-point `sglang.srt.platforms` | 让引擎发现你的平台 |
| ③ ServerArgs 默认值 | `apply_server_args_defaults()` | dtype、page size、关闭不支持特性 |
| ④ Attention backend | `get_default_attention_backend()` + 自写后端 | 见文档 06 |
| ⑤ KV 内存池 | `get_mha_kv_pool_cls()` / `get_mla_kv_pool_cls()` | 默认 MHA/MLA 池通常可复用 |
| ⑥ 图执行 | `get_graph_runner_cls()` + `support_cuda_graph()` | 不支持图就先关掉 |
| ⑦ 编译后端 | `get_compile_backend()` / `get_piecewise_backend_cls()` | 默认 inductor |
| ⑧ 量化支持 | `supported_quantization` + `get_quantization_config()` | 先支持 bf16/fp16 |
| ⑨ 算子快速路径 | `MultiPlatformOp` 或 `is_*()` 分支 | RMSNorm/RoPE/SiLU 等 |
| ⑩ 通信后端 | `get_torch_distributed_backend_str()` / `get_communicator_class()` | nccl/xccl/hccl/自研 |
| ⑪ 模型适配 | 必要时给模型文件加设备分支 | 多数模型零改动可跑 |

下面按实现层次展开。

## 2. 抽象层:`platforms/`(接口与分发)

### 2.1 类层级

```
DeviceMixin                                    (设备身份 + 设备操作)
├── CudaDeviceMixin ── CudaSRTPlatform         (NVIDIA)
│   └── RocmDeviceMixin ── RocmSRTPlatform     (AMD,复用 CUDA shim)
├── CpuDeviceMixin ── CpuSRTPlatform           (纯 CPU)
├── XpuDeviceMixin ── XpuSRTPlatform           (Intel GPU)
└── SRTPlatform(DeviceMixin)                   (基类,也是兜底)
```

官方给出的 OOT(out-of-tree)扩展模式:

```10:17:python/sglang/srt/platforms/device_mixin.py
    DeviceMixin
    ├── MyDeviceMixin(DeviceMixin)        # vendor-specific device operations
    ├── SRTPlatform(DeviceMixin)          # + graph runner, KV pool, …
    │   └── MySRTPlatform(SRTPlatform, MyDeviceMixin)
    └── MMPlatform(DeviceMixin)           # + attention backend, VAE, …
        └── MyMMPlatform(MMPlatform, MyDeviceMixin)
```

第三方**不要改主仓**:继承 `SRTPlatform` + 自己的 `DeviceMixin`,在独立 pip 包里实现。

### 2.2 DeviceMixin:设备身份与操作

**身份查询是「终态方法」,不要重写**——它们通过比较 `_enum` 判断:

- `_enum: PlatformEnum`:`CUDA / ROCM / CPU / XPU / MUSA / NPU / TPU / MPS / OOT / UNSPECIFIED`。第三方平台应使用 `PlatformEnum.OOT`。
- `is_cuda()/is_rocm()/...`、`is_cuda_alike()`(CUDA/ROCM/MUSA)、`is_out_of_tree()`。

**必须实现的设备操作**(核心代码通过这些调用你的实现):

```python
get_device_total_memory(device_id=0) -> int       # 总显存(profile 用)
get_current_memory_usage(device=None) -> float    # 当前占用(GB)
is_pin_memory_available(device=None) -> bool
```

**建议实现的规划接口**(部分已被接入,其余逐步接入):

```python
get_device(device_id=0) -> str
set_device(device)
get_device_capability(device_id=0) -> DeviceCapability | None
get_available_memory(device_id=0) -> tuple[int, int]
empty_cache() / synchronize()
get_torch_distributed_backend_str() -> str       # 默认查表,fallback "gloo"
get_communicator_class() -> type | None          # 自定义集合通信
inference_mode() / seed_everything(seed)
get_torch_profiler_activity_str() / get_torch_profiler_activity()
```

### 2.3 SRTPlatform:SRT 专属工厂与能力开关

```26:38:python/sglang/srt/platforms/interface.py
class SRTPlatform(DeviceMixin):

    Base class for SRT hardware platform backends.

    Inherits device identity queries and operations from DeviceMixin.
    Adds SRT-specific factory methods, capability flags, and lifecycle hooks.

    OOT platforms should subclass SRTPlatform and override the methods
    relevant to their hardware.
    """

    # SRT-specific class-level attribute
    supported_quantization: list[str] = []
```

**生命周期钩子**:

- `apply_server_args_defaults(server_args)`:参数解析后调用,**覆盖默认值的官方入口**;
- `init_backend()`:每个 worker 进程初始化时调用一次(导入你的 SDK、设全局开关)。

**子系统工厂**(核心代码运行时向你「要实现」):

```python
get_default_attention_backend() -> str        # 默认 attention 后端名
get_graph_runner_cls() -> type                # CUDA Graph runner 类
get_mha_kv_pool_cls() -> type                 # MHA KV 池
get_mla_kv_pool_cls() -> type                 # MLA KV 池
get_dsa_kv_pool_cls() -> type                 # DSV4 稀疏索引池
get_paged_allocator_cls() -> type             # 分页分配器
get_compile_backend(mode=None) -> str         # 默认 "inductor"
get_piecewise_backend_cls() -> type           # 分段编译后端
get_quantization_config(name) -> Optional[type]  # None = 用内置
```

**能力开关**(默认全 False,安全保守):

```python
supports_fp8() -> bool
support_cuda_graph() -> bool            # decode 图捕获
support_piecewise_cuda_graph() -> bool  # prefill/extend 分段编译
```

**算子分发键**:

- `get_dispatch_key_name() -> str`,默认 `"native"`。配合 `MultiPlatformOp`(见 §5)。

### 2.4 核心代码怎么用平台:current_platform

`platforms/__init__.py` 提供**惰性单例**:

```163:173:python/sglang/srt/platforms/__init__.py

def __getattr__(name: str):
    """Lazy initialization of current_platform on first access."""
    if name == "current_platform":

        if _current_platform is None:
            _current_platform = _resolve_platform()
        return _current_platform
```

任何模块 `from sglang.srt.platforms import current_platform`,首次访问时触发解析。全仓约 **146 处**调用,分布最多的场景:`synchronize()`(26)、`is_out_of_tree()`(22)、`empty_cache()`(15),其次是各工厂方法与能力开关。

## 3. 平台发现:entry-point 插件机制

`_resolve_platform()` 的决策顺序:

1. **设了 `SGLANG_PLATFORM=<name>`**:只在 entry-point 组 `sglang.srt.platforms` 里按名字找,调其 `activate()`:
   - 返回类的全限定名 → 加载并校验为 `SRTPlatform` 子类 → 实例化;
   - 找不到名字 → 报错并列出可用插件;
   - `activate()` 返回 None → 视为硬件不在场,报错。
2. **未设 `SGLANG_PLATFORM`**:加载组内**所有**插件的 `activate()`:
   - 0 个激活 → 回退链:`SGLANG_USE_CPU_ENGINE=1`→CPU;`torch.cuda` 可用→CUDA;ROCm;XPU;都没有→基类 `SRTPlatform`;
   - 恰好 1 个 → 用它;
   - 多个 → 报错,要求用户设 `SGLANG_PLATFORM` 消歧。

组名常量:

```28:29:python/sglang/srt/plugins/__init__.py
PLATFORM_PLUGINS_GROUP = "sglang.srt.platforms"
GENERAL_PLUGINS_GROUP = "sglang.srt.plugins"
```

### 3.1 你的插件包长什么样

```toml
# pyproject.toml
[project]
name = "sglang-mydevice"

[project.entry-points."sglang.srt.platforms"]
mydevice = "sglang_mydevice.plugin:activate"
```

```python
# sglang_mydevice/plugin.py
def activate():
    """返回平台类全限定名;硬件不在场时返回 None。"""
    if not mydevice_is_available():
        return None
    return "sglang_mydevice.platform:MyDeviceSRTPlatform"
```

```python
# sglang_mydevice/platform.py
from sglang.srt.platforms.device_mixin import DeviceMixin, PlatformEnum
from sglang.srt.platforms.interface import SRTPlatform

class MyDeviceMixin(DeviceMixin):
    _enum = PlatformEnum.OOT
    device_name = "mydevice"
    device_type = "mydevice"          # torch.device 的 type 字符串

    def get_device_total_memory(self, device_id=0): ...
    def get_current_memory_usage(self, device=None): ...
    def get_torch_distributed_backend_str(self): return "mccl"  # 你的集合通信
    ...

class MyDeviceSRTPlatform(MyDeviceMixin, SRTPlatform):
    supported_quantization = []       # 起步只支持非量化

    def apply_server_args_defaults(self, server_args):
        server_args.page_size = 1
        # 关闭暂不支持的特性
        ...

    def get_default_attention_backend(self): return "mydevice"
    def get_mha_kv_pool_cls(self):
        from sglang.srt.mem_cache.memory_pool import MHATokenToKVPool
        return MHATokenToKVPool
    def support_cuda_graph(self): return False   # 起步先关
```

启动:`pip install sglang-mydevice && SGLANG_PLATFORM=mydevice python -m sglang.launch_server ...`

### 3.2 通用插件钩子(Hook)

除平台插件外,`plugins/hook_registry.py` 提供 BEFORE/AFTER/AROUND/REPLACE 四类钩子,可 monkey-patch 任意目标函数(例如给某接口加日志、替换某实现)。`load_plugins()` 在 `launch_server.py`、`cli/serve.py`、`engine.py` 等多处被调用,保证插件尽早生效。参考测试:`test/registered/unit/plugins/test_load_plugins.py`。

## 4. 实现层:`hardware_backend/`(树内设备的参考实现)

`hardware_backend/` 是**实现**层,放具体设备的内核、attention 后端、graph runner、内存池。树内已有的参考实现(适配时抄作业的宝库):

| 目录 | 设备 | 值得学的内容 |
|---|---|---|
| `npu/`(最大) | 华为昇腾 | 完整 attention 后端家族(含 MLA/GDN/DSv4)、graph runner、MoE 算子、量化、内存池 |
| `xpu/` | Intel GPU | graph runner、full graph backend、FLA 内核 |
| `musa/` | 摩尔线程 | FA3 风格 attention 后端、topk 内核、torch patch |
| `cpu/` | CPU(AMX) | AWQ/GPTQ 量化内核 |
| `gpu/` | NVIDIA | Marlin 系量化内核(对照实现) |
| `mlx/` | Apple Silicon | 完整另起炉灶的运行时变体(model_runner/scheduler mixin/KV 池) |

**核心代码进入 hardware_backend 的两条路**:

1. 显式设备分支导入,如 `layers/moe/fused_moe_triton/layer.py` 里 `if _is_npu: from sglang.srt.hardware_backend.npu.moe.fuseep import forward_fuseep`;
2. 注册表,如 `attention_registry.py` 的 `"ascend"` 工厂导入 `hardware_backend/npu/attention/ascend_backend.py`。

> 长期方向(官方文档 plugin.mdx 所述):树内实现逐步迁到插件架构,`if device == ...` 分支收敛为多态分发。你现在写的新设备适配,应优先走插件路线。

## 5. 算子分发:三条路径并存

核心代码里「同一个算子在不同设备上用不同实现」有三种机制,适配时都会遇到:

### 路径 A:MultiPlatformOp(推荐的多态基类)

`layers/utils/multi_platform.py`。算子层继承它,实现 `forward_native` / `forward_cuda` 等,`dispatch_forward()` 在构造时一次性绑定:

```109:134:python/sglang/srt/layers/utils/multi_platform.py
    def dispatch_forward(self):
        # OOT platform dispatch: check registry then method lookup
        if current_platform.is_out_of_tree():
            key = current_platform.get_dispatch_key_name()
            oot = self._oot_forward_registry.get(key, {})
            if type(self) in oot:
                return oot[type(self)].__get__(self)
            method = getattr(self, f"forward_{key}", None)
            if method is not None:
                return method
            return self.forward_native

        if _is_cuda:
            return self.forward_cuda
        elif _is_hip:
            return self.forward_hip
        ...
        else:
            return self.forward_native
```

**OOT 适配者的两个选择**:

- 在平台子类里定义 `forward_<dispatch_key>` 方法;或
- 调 `MultiPlatformOp.register_oot_forward(op_cls, fn, platform_key)` 在插件里外部注册。

默认回退是 `forward_native`(纯 PyTorch),所以**任何设备最低限度都能跑**——正确性兜底,性能再优化。

### 路径 B:模块级 is_*() 分支(遗留主流)

`utils/common.py` 提供 `is_cuda()/is_hip()/is_npu()/is_xpu()/is_musa()/is_hpu()/is_cpu()/is_mps()/is_cuda_alike()`,以及 `get_device()`(探测顺序 cpu→cuda→xpu→npu→hpu→musa→mps)。树内大量代码用这些做条件导入与分支。你读代码时看到 `_is_npu` 之类,即此机制。

### 路径 C:is_out_of_tree() + 工厂方法(插件时代模式)

总是先查 OOT,再走 is_*() 级联。典型形状:

```55:62:python/sglang/srt/compilation/backend.py
    if current_platform.is_out_of_tree():
        backend_cls = current_platform.get_piecewise_backend_cls()
    elif is_xpu():
        backend_cls = XPUPiecewiseBackend
    elif is_npu():
        backend_cls = NPUPiecewiseBackend
    else:
        backend_cls = CUDAPiecewiseBackend
```

同样形状还出现在:KV 池选择(`memory_pool.py` 的 `get_mha_kv_pool_cls`)、graph runner(`cuda_graph_setup.py` 的 `get_graph_runner_cls`)、量化配置(`layers/quantization/__init__.py` 的 `get_quantization_config`)、attention 默认值(`server_args.py`)、显存/编译器查询(`utils/common.py`)。

## 6. ServerArgs 与设备校验:适配要过的关卡

1. **设备白名单**:`configs/device_config.py` 的 `SUPPORTED_DEVICES = ["cuda","xpu","hpu","cpu","npu","musa","mps"]`,**但 OOT 平台无条件放行**:

```10:22:python/sglang/srt/configs/device_config.py
SUPPORTED_DEVICES = ["cuda", "xpu", "hpu", "cpu", "npu", "musa", "mps"]


class DeviceConfig:
    ...
    def __init__(self, device: str = "cuda", gpu_id: int = -1) -> None:
        if device in SUPPORTED_DEVICES or current_platform.is_out_of_tree():
            self.device_type = device
        else:
            raise RuntimeError(f"Not supported device type: {device}")
```

即:OOT 平台可以用任意 `device_type`,无需改主仓。

2. **默认值注入**:`ServerArgs.__post_init__` 末尾:

```3479:3480:python/sglang/srt/server_args.py
        # Allow OOT platform plugins to apply server args defaults.
        current_platform.apply_server_args_defaults(self)
```

3. **attention 默认值**:OOT 平台短路到 `get_default_attention_backend()`;树内设备走 `_get_default_attn_backend()` 的硬件分支。
4. **采样后端**:`--sampling-backend` 可选 `flashinfer/pytorch/ascend`;新设备先用 `pytorch`,再逐步提供原生实现(可注册,见文档 08)。

## 7. 端到端适配路线图(按里程碑)

**M0 · 环境打通(1 周级)**
- 目标设备上装好你的 PyTorch 分支(`torch.device("mydevice")` 可用、基本算子齐全)。
- 写最小 `activate()` + `MyDeviceSRTPlatform`(只实现 §2.2 的三个必须项),`SGLANG_PLATFORM` 能解析到你的类。

**M1 · 数值正确(里程碑:能出正确文本)**
- `--attention-backend torch_native --disable-cuda-graph --disable-radix-cache` 起步;
- 修 dtype/device 假设(`device_type`、`empty_cache`、`synchronize`);
- 用小模型(如 Qwen2-0.5B)对 HF transformers 输出;
- 逐个修复报错——90% 是「某处 hardcode 了 cuda」。

**M2 · 特性补齐**
- 实现自己的 attention backend(文档 06),替换 torch_native;
- 打开 radix cache(默认),验证前缀复用;
- 内存池如需定制(布局/量化)实现 `get_mha_kv_pool_cls`;
- TP:实现/接入通信后端(`get_torch_distributed_backend_str` + 必要时自定义 communicator)。

**M3 · 性能**
- graph runner(若设备支持图):`support_cuda_graph()` + `get_graph_runner_cls()`;
- 分段编译:`get_piecewise_backend_cls()`;
- 算子快速路径:通过 MultiPlatformOp 注册 RMSNorm/RoPE/激活等;
- MoE 支持(topk/grouped GEMM)、量化(先 W8A8,再 FP8)。

**M4 · 产品化**
- 补 CI 测试(参考 `test/registered/npu/`、`xpu/`、`musa/`);
- 写文档(参考 `docs_new/docs/hardware-platforms/` 各平台页);
- 跟踪上游:`platforms/` 与 `hardware_backend/` 演进较快,定期 rebase。

## 9. 本篇要点回顾

1. 适配 = 继承 `SRTPlatform` + `DeviceMixin`,以独立 pip 包 + entry-point 插件接入,不改主仓。
2. `current_platform` 惰性单例是核心分发点;全仓 146+ 处调用,覆盖显存、同步、工厂、能力开关。
3. `hardware_backend/` 是树内实现层,NPU/XPU/MUSA/MLX 是最好的「抄作业」对象。
4. 算子分发三路径:MultiPlatformOp 多态(推荐)、is_*() 分支(遗留)、is_out_of_tree()+工厂(新模式)。
5. 路线图:M0 能解析 → M1 torch_native 出正确结果 → M2 自研 attention + TP → M3 图与算子优化 → M4 CI 与文档。
