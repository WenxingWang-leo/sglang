# 02 · 请求生命周期与核心数据流

> 本篇追踪一个 `generate` 请求从 HTTP 进入到文本返回的全过程,覆盖所有关键数据结构。
> 读懂这一篇,你就掌握了 SGLang 的「血管系统」——之后所有优化都发生在某一段血管上。

---

## 1. 全景图

```
Client
  │  POST /generate {text, sampling_params, stream}
  ▼
[主进程] http_server.py
  │  校验参数、应用 chat template(若是 /v1/chat/completions)
  ▼
[主进程] TokenizerManager.generate_request()
  │  ① 分词: text → input_ids
  │  ② 构造 TokenizedGenerateReqInput(纯数据对象)
  │  ③ ZMQ send ─────────────────────────────┐
  │                                          ▼
  │  [Scheduler 进程] Scheduler.event_loop_*
  │     recv_requests() → process_input_requests()
  │       → Req 对象入 waiting_queue
  │     get_next_batch_to_run()  拼批(extend/decode)
  │     run_batch() → ModelRunner.forward() → GPU
  │     process_batch_result() → 采样出的 token 追加进 Req
  │       └─ 未完成: 留在 running_batch 继续 decode
  │       └─ 完成/中止: BatchTokenIDOutput
  │              │  ZMQ send ──────────────────────┐
  ▼                                                 ▼
[主进程] ReqState 收到事件            [Detokenizer 进程] 增量解码
  │  组装最终输出                     token ids → 文本片段
  ▼                                   BatchStrOutput 回传主进程
Client 收到 JSON / SSE
```

---

## 2. 入口:HTTP 与 TokenizerManager

### 2.1 HTTP 层(`entrypoints/http_server.py`)

- `/generate`:原生接口,直接接收 `text` 或 `input_ids`。
- `/v1/chat/completions` / `/v1/completions`:OpenAI 兼容接口,先套 chat template 变成纯文本。
- 两者最终都调用 `tokenizer_manager.generate_request(obj, request)`,返回一个异步迭代器;`stream=True` 时以 SSE 逐块推送。

### 2.2 TokenizerManager(`managers/tokenizer_manager.py`)

职责清单:

1. **分词**:HuggingFace tokenizer 把文本变成 `input_ids`(多模态请求在这里并行做图像/音频预处理)。
2. **构造请求对象**:生成 `GenerateReqInput`(API 层)→ 校验 → 转成 `TokenizedGenerateReqInput`(调度层)。
3. **注册结果通道**:为本请求创建一个 `ReqState`(内含 `asyncio.Event` + 结果队列),按 `rid`(请求 ID)登记。
4. **ZMQ 发送**给 scheduler;TP>1 时只需发给 rank0——rank0 会在 `recv_requests()` 里把原始请求对象广播给其余 rank,各 rank 随后独立执行相同的拼批逻辑(机制详见文档 03)。
5. **回收结果**:detokenizer 把 `BatchStrOutput` 发回,`_handle_batch_output` 按 `rid` 找到 `ReqState` 并 set event,HTTP 层随之返回。

> 抽象要点:**主进程只做「文本↔token」的边界转换与请求路由,任何 GPU 相关的事都在 scheduler 进程**。

### 2.3 关键数据结构:请求的三次变身

| 阶段 | 类型 | 所在进程 | 内容 |
|---|---|---|---|
| API 层 | `GenerateReqInput` | 主进程 | 原始文本/参数/图片 |
| 传输层 | `TokenizedGenerateReqInput` | 跨进程(ZMQ) | `input_ids` + `sampling_params` + `rid` |
| 调度层 | `Req` | scheduler 进程 | 运行时状态机(见下) |

## 3. 调度层:`Req` —— 请求的运行时化身

定义在 `managers/schedule_batch.py`。一个 `Req` 贯穿 prefill 到 decode 结束,重要字段:

```python
class Req:
    rid: str                      # 唯一 ID,贯穿全链路
    origin_input_ids: array       # 原始 prompt token ids
    output_ids: array             # 已生成的 token ids

    # —— 本步要喂进模型的 token 范围 ——
    full_untruncated_fill_ids: array   # = origin_input_ids + output_ids(惰性同步)
    extend_range: Optional[Range]      # 本步 extend 的 [start, end) 区间

    # —— 内存与缓存 ——
    req_pool_idx: int             # 在 ReqToTokenPool 中的行号
    prefix_indices: Tensor        # RadixCache 命中的前缀 KV 槽位
    last_node: TreeNode           # 命中的最深树节点(持锁)
    cache_protected_len: int      # 已入树保护的长度

    # —— 采样 ——
    sampling_params: SamplingParams
    return_logprob: bool

    # —— 状态 ——
    finished_reason: Optional[FINISHED_*]   # None = 还在跑
    grammar: ...                            # 约束解码(XGrammar)
```

**这里有个容易踩的设计细节**:`Req` 没有简单的 `fill_ids` 字段,而是「一个全量数组 + 一个区间」的组合:

- `full_untruncated_fill_ids` 是 prompt 与已生成 token 的**完整拼接**,由 `_refresh_fill_ids()` 惰性维护(它靠长度差推断已有多少输出 token 被拼进去了,所以**任何保持长度不变的原地改写都会静默损坏它**,代码里对此有显式注释警告);
- `extend_range: Range(start, end)` 标记本步真正要送进模型的切片;
- 取值统一走 `get_fill_ids()`,即 `full_untruncated_fill_ids[:extend_range.end]`。

这样设计是为了让 **chunked prefill** 自然表达:一个长 prompt 被切成多段,每段只是同一个数组上 `extend_range` 的推进,不需要反复拷贝 token 列表。

请求的**长度**恒等于 `len(origin_input_ids) + len(output_ids)`;每一步 decode 使 `output_ids` 增长 1(投机解码时一次可能接受多个)。

## 4. 批:`ScheduleBatch` 与 `ForwardMode`

### 4.1 ScheduleBatch

`ScheduleBatch` 是一组 `Req` 的视图,负责把 Python 列表「张量化」成 GPU 输入:

- `reqs: List[Req]`、`req_pool_indices`、`seq_lens`、`input_ids`、`out_cache_loc`(新 KV 写入槽位)。
- `prepare_for_extend()` / `prepare_for_decode()`:分配内存、填写上述张量(细节见文档 04)。
- `filter_batch()` / `merge_batch()`:请求完成时剔除、prefill 批与 decode 批合并。

### 4.2 ForwardMode(`model_executor/forward_batch_info.py`)

```98:123:python/sglang/srt/model_executor/forward_batch_info.py
class ForwardMode(IntEnum):
    # Extend the inputs. (prefill)
    EXTEND = auto()
    # Decode with one token per request.
    DECODE = auto()
    ...
    MIXED = auto()
    IDLE = auto()
    ...
    TARGET_VERIFY = auto()      # 投机解码的 target 校验
    DRAFT_EXTEND_V2 = auto()    # 投机解码的 draft 扩展
```

- **EXTEND**:prefill 或 chunked prefill 续算,一次吃多个新 token。
- **DECODE**:每个请求恰好 1 个新 token,访存密集型。
- **MIXED**:prefill 与 decode 混在一个 batch(chunked prefill 常态)。
- **IDLE**:DP attention 下某 rank 无活干时的占位模式。
- 投机解码引入 `TARGET_VERIFY` / `DRAFT_EXTEND_V2`(树状校验)。

## 5. 执行:run_batch → ModelRunner.forward

`Scheduler.run_batch(batch)`(`scheduler.py:3470`)做两件事:

1. `batch.prepare_for_*()` 完成内存分配与张量组装。
2. 调 `self.tp_worker.forward_batch_generation(batch)` → `ModelRunner.forward(forward_batch)`:
   - 根据 `forward_mode` 选择路径:decode 优先走 **CUDA Graph replay**;extend 走 eager 或分段编译。
   - 模型前向产出 logits → 采样 → 返回 `GenerationBatchResult`(含 `next_token_ids`)。
3. (overlap 模式下)采样可以异步发射,与下一批的 CPU 工作重叠。

`ForwardBatch` 是传进模型的最终对象,核心字段:

```415:429:python/sglang/srt/model_executor/forward_batch_info.py
    forward_mode: ForwardMode
    batch_size: int
    input_ids: torch.Tensor
    # The indices of requests in the req_to_token_pool
    req_pool_indices: torch.Tensor
    # The sequence length
    seq_lens: torch.Tensor
    # The indices of output tokens in the token_to_kv_pool
    out_cache_loc: torch.Tensor
    # The sum of all sequence lengths
    seq_lens_sum: int
```

extend 模式另有 `extend_seq_lens / extend_prefix_lens / extend_start_loc` 描述每个请求的变长片段。

## 6. 结果回收:process_batch_result

`Scheduler.process_batch_result(batch, result)`(`scheduler.py:3756`)逐请求处理:

1. 把新 token 追加进 `req.output_ids`。
2. 检查停止条件:EOS、`max_new_tokens`、stop strings、grammar 终止。
3. **未完成** → 留在 `running_batch`,下一轮 decode。
4. **完成** → `tree_cache.cache_finished_req(req)`:把整段 KV 槽位插入 RadixCache(供后续请求复用),释放 `req_pool_idx`。
5. 组装 `BatchTokenIDOutput`(rids + token ids + logprobs),经 ZMQ 发往 detokenizer。

Detokenizer 用**增量解码**处理 UTF-8 跨 token 边界,输出 `BatchStrOutput` 回主进程;主进程按 `rid` 唤醒等待中的 HTTP 协程。

## 7. 一条请求的时间线(示例)

设 prompt 1000 tokens,生成 10 tokens,RadixCache 命中 800:

| 步骤 | 动作 | 涉及对象 |
|---|---|---|
| t0 | 分词完成,`TokenizedGenerateReqInput` 发出 | TokenizerManager |
| t1 | 创建 `Req`,入 `waiting_queue` | Scheduler |
| t2 | `match_prefix` 命中 800 tokens → `prefix_indices` | RadixCache |
| t3 | `PrefillAdder` 放行;`alloc_for_extend` 分配 200 个新槽位 | schedule_policy / allocation |
| t4 | EXTEND 前向:只算 200 tokens(省了 80% 计算) | ModelRunner |
| t5 | 采样得第 1 个输出 token | Sampler |
| t6..t15 | 10 轮 DECODE,每轮 1 token;CUDA Graph replay | Scheduler |
| t16 | 命中停止;`cache_finished_req` 把 1010 tokens 的 KV 入树 | RadixCache |
| t17 | Detokenizer 增量解码,HTTP 返回全部文本 | 主进程 |

---

## 8. 本篇要点回顾

1. 请求经历 `GenerateReqInput → TokenizedGenerateReqInput → Req` 三次变身,跨三个进程。
2. `Req` 是调度层的状态机;`ScheduleBatch` 是批的张量化视图;`ForwardMode` 决定前向路径。
3. 主循环每圈固定做:`recv → get_next_batch_to_run → run_batch → process_batch_result`。
4. 请求结束时 KV 不销毁,而是插入 RadixCache —— 这是 SGLang 的灵魂。
5. 输出路径是 token ids → detokenizer 增量解码 → 文本,与调度完全解耦。
