# 01 · SGLang 架构总览与启动流程

> 目标读者:想从「会用」进阶到「能改、能适配」的开发者。
> 本篇建立全局心智模型:进程拓扑、模块边界、启动时序。后续所有深度文档都以此为地图。
> 所有路径均相对于仓库根目录 `sglang/`,核心运行时位于 `python/sglang/srt/`。

---

## 1. 一句话理解 SGLang

SGLang 是一个**面向大语言模型(LLM)与多模态模型的高性能推理引擎**,核心卖点有两个:

1. **RadixAttention(基数树前缀缓存)**:用一棵 radix tree 缓存所有请求的公共前缀 KV,使多轮对话、共享 system prompt、few-shot 等场景的重复前缀计算被直接复用。
2. **高度结构化的调度与执行流水线**:把「收请求 → 拼批 → 前向 → 采样 → 解码回传」拆成多个独立进程,用连续批处理(continuous batching)+ 重叠(overlap)把 GPU 打满。

从工程角度,SGLang 的 Python 运行时(`sglang.srt`,即 SGLang Runtime / SRT)是**多进程 + ZMQ 消息**架构,而不是单进程多线程。理解这一点是读懂一切的前提。

## 2. 顶层代码地图

```
sglang/
├── python/sglang/
│   ├── srt/                      # ★ 核心运行时(SRT)—— 你 90% 的时间在这里
│   │   ├── entrypoints/          # 入口:engine.py(进程编排)、http_server.py(FastAPI)
│   │   ├── managers/             # ★ 三大进程逻辑:scheduler / tokenizer_manager / detokenizer
│   │   ├── model_executor/       # ModelRunner:前向调度、CUDA Graph、ForwardBatch
│   │   ├── model_loader/         # 权重加载器(DefaultModelLoader 等)
│   │   ├── models/               # ★ 每个模型一个文件,通过 EntryClass 注册
│   │   ├── layers/               # ★ 模型积木:linear / attention / moe / rotary / quantization
│   │   │   └── attention/        # ★ attention backend 抽象与各实现
│   │   ├── mem_cache/            # ★ KV 内存池、RadixCache、分配器
│   │   ├── sampling/             # 采样参数与批量采样信息
│   │   ├── distributed/          # TP/PP 通信(源自 vLLM/Megatron)
│   │   ├── platforms/            # ★ 硬件平台抽象层(DeviceMixin / SRTPlatform)
│   │   ├── hardware_backend/     # ★ 非 NVIDIA 设备的内核/实现(NPU/XPU/MUSA/MLX/CPU)
│   │   ├── disaggregation/       # Prefill/Decode 分离(PD 分离)
│   │   ├── speculative/          # 投机解码(EAGLE/MTP 等)
│   │   └── server_args.py        # ★ 所有 CLI/引擎参数定义
│   ├── api/                      # Python 客户端 API(Engine、openai 风格)
│   └── lang/                     # SGLang 前端 DSL(结构化生成编程语言)
├── sgl-kernel/                   # 预编译 AOT CUDA 内核(独立打包)
├── test/registered/              # CI 测试(按类别分子目录)
└── docs_new/                     # Mintlify 官方文档源
```

**记住这条主线**:`entrypoints → managers → model_executor → models/layers → mem_cache`,外加横切的 `platforms` 与 `distributed`。

## 3. 进程拓扑:谁在跑,谁跟谁说话

SGLang 启动后,**一个服务端点 = 多个操作系统进程**。默认(单节点、TP=N)拓扑如下:

```
                      ┌──────────────────────────────────────────────┐
                      │  主进程 (rank0 进程)                          │
                      │   ├─ HTTP Server (FastAPI, uvicorn)          │
                      │   └─ TokenizerManager (分词 + 请求路由)        │
                      └───────────────┬──────────────────────────────┘
                                      │  ZMQ ipc://  (Python 对象序列化)
                 ┌────────────────────┼─────────────────────┐
                 ▼                    ▼                     ▼
        ┌────────────────┐   ┌────────────────┐   ┌────────────────────┐
        │ Scheduler 进程   │   │ Scheduler 进程   │   │ DetokenizerManager  │
        │ (TP rank 0)     │   │ (TP rank 1..N-1)│   │  (增量解码)          │
        │  事件循环 + 拼批  │   │  从 rank0 广播   │   │                    │
        │  + ModelRunner  │   │  同步执行        │   │                    │
        │  + GPU 前向      │   │                │   │                    │
        └────────────────┘   └────────────────┘   └────────────────────┘
                 │                                        ▲
                 └──────────── ZMQ 回传 token id ──────────┘
```

关键事实:

- **TokenizerManager 在主进程**:负责把文本分词、校验采样参数,然后把 `TokenizedGenerateReqInput` 通过 ZMQ 发给 Scheduler。它**不做 GPU 计算**。
- **每个 TP rank 一个 Scheduler 进程**:rank0 是「主 scheduler」,其余 rank 通过 TP broadcast 跟随 rank0 的调度决策,保证所有 rank 的批一致。
- **DetokenizerManager 独立进程**:把 GPU 产出的 token id 增量解码回文本,避免阻塞主调度。
- **进程间用 ZMQ ipc socket**,端口由 `PortArgs.init_new(server_args)` 统一分配。

> 为什么拆这么多进程?因为 Python GIL + GPU 异步执行。把分词/调度/解码拆到独立进程,能让 CPU 工作与 GPU 前向**真正并行**(这正是 `event_loop_overlap` 的基础,见文档 03)。

### 3.1 多卡/多节点时的变化

| 配置 | 进程布局变化 |
|---|---|
| TP=N | N 个 Scheduler 进程(rank0..N-1),每进程绑一张卡 |
| PP=M | 每个 TP 组内再按 PP 切层,`initialize_model_parallel(pp_size=…)` |
| DP attention | 额外一个 `DataParallelController` 进程做请求分发,每 DP worker 一组 TP scheduler |
| 多节点 | `node_rank>=1` 的节点只跑 scheduler,不跑 tokenizer/detokenizer;用 NCCL/RDMA 组网 |

## 5. 启动流程:从 `Engine()` 到第一个请求可服务

入口是 `Engine`(`entrypoints/engine.py`)。核心方法是 `_launch_subprocesses`,它把「参数 → 端口 → 进程 → 就绪」串起来。时序如下:

```
Engine.__init__(server_args)
  │
  ├─ _launch_subprocesses(server_args, ...)
  │    │
  │    ├─ configure_logger / _set_envs_and_config      # 日志、全局配置
  │    ├─ load_plugins()                               # 加载第三方平台插件(关键,见文档 07)
  │    ├─ server_args.check_server_args()              # 参数合法性
  │    ├─ PortArgs.init_new(server_args)               # 分配 ZMQ ipc 端口
  │    │
  │    ├─ _launch_scheduler_processes(...)             # mp.spawn 出每个 TP rank 的 scheduler
  │    │      └─ 每个 scheduler 进程内:
  │    │           run_scheduler_process()
  │    │             └─ Scheduler.__init__()
  │    │                  ├─ init_model_worker()       # ★ 建 ModelRunner(见下)
  │    │                  ├─ 初始化 tree_cache / 内存池
  │    │                  └─ 进入 event_loop_normal / event_loop_overlap
  │    │
  │    ├─ _launch_detokenizer_processes(...)           # detokenizer 子进程
  │    │
  │    └─ init_tokenizer_manager_func(...)             # 主进程内构造 TokenizerManager
  │         └─ TokenizerManager 连上 scheduler 的 ZMQ socket
  │
  └─ 返回 Engine 实例(async_generate / generate 可用)
```

### 5.1 Scheduler 进程内的初始化(`Scheduler.__init__`)

这是整个系统最重的一段,顺序大致是:

1. **`init_model_worker()`**:构造 `TpModelWorker` → `ModelRunner`。
   - `ModelRunner.__init__` → `initialize()`:
     - 解析 `DeviceConfig` / `ModelConfig`。
     - `load_model()`:通过 `model_loader.get_model_loader()` 拿到加载器,实例化模型类,加载权重。
     - **显存 profiling**:空跑一次前向,测量峰值显存,推算 `max_total_num_tokens`(能缓存多少 token 的 KV)。这是「显存 → KV 容量」的关键换算(见文档 04)。
     - `alloc_memory_pool()`:真正分配 KV 内存池 + `ReqToTokenPool` + RadixCache。
     - 若启用 CUDA Graph,做 graph capture。
2. 构造 `tree_cache`(默认 `RadixCache`)与 `token_to_kv_pool_allocator`。
3. 建立与其它进程/ZMQ 的连接。
4. 进入主事件循环。

> 关键点:**KV 容量不是用户指定的,而是测出来的**。`max_total_num_tokens = (可用显存 − 运行时 slack) ÷ 每 token KV 字节数`。这个设计让 SGLang 能自动吃满显存。

### 5.2 HTTP Server 的角色

`http_server.py` 用 FastAPI 暴露 OpenAI 兼容端点。它本身很薄:把请求转给主进程的 `TokenizerManager.generate_request`,拿到异步结果后以 SSE/JSON 返回。**真正的智能全在 Scheduler**。

## 6. `ServerArgs`:一切的旋钮

`server_args.py` 是一个巨型 dataclass,定义了所有 CLI / 引擎参数。按语义分组(节选高频项):

| 组 | 代表参数 | 说明 |
|---|---|---|
| 模型 | `--model-path`、`--dtype`、`--kv-cache-dtype` | 模型与精度 |
| 调度 | `--max-running-requests`、`--chunked-prefill-size`、`--schedule-policy` | 批处理行为 |
| 内存 | `--mem-fraction-static`、`--max-total-tokens` | 显存划分 |
| 注意力 | `--attention-backend`(`flashinfer/triton/fa3/torch_native/ascend/…`) | 选择 attention 实现 |
| 采样 | `--sampling-backend`(`flashinfer/pytorch/ascend`) | 采样内核 |
| 并行 | `--tp-size`、`--dp-size`、`--ep-size`、`--pp-size` | 并行拓扑 |
| 设备 | `--device`(`cuda/xpu/npu/cpu/musa/hpu`) | 目标硬件 |
| 前缀缓存 | `--disable-radix-cache`、`--enable-hierarchical-cache` | 缓存策略 |

每个参数在 `__post_init__` 中会按设备做适配(如 `_handle_npu_backends`、`_handle_cpu_backends`),最终 OOT 平台通过 `current_platform.apply_server_args_defaults(self)` 注入自己的默认值。这条链路是第三方适配的重要切入点(见文档 07)。

## 7. 阅读路线建议

- **先跑起来**:`python -m sglang.launch_server --model-path <小模型>`,观察启动日志里 `max_total_num_tokens`、`KV Cache is allocated`、`The server is fired up` 等关键行。
- **再看进程**:用 `ps`/`py-spy` 看主进程 + N 个 scheduler + detokenizer。
- **然后按本系列顺序读**:02 请求生命周期 → 03 调度器 → 04 内存与 RadixCache → 05 模型层 → 06 attention backend → 07 硬件适配。

---

## 8. 本篇要点回顾

1. SGLang 是**多进程 + ZMQ**架构:主进程(TokenizerManager) + 每 TP rank 一个 Scheduler + 一个 Detokenizer。
2. 核心代码在 `python/sglang/srt/`,主线是 `entrypoints → managers → model_executor → models/layers → mem_cache`。
3. 启动由 `Engine._launch_subprocesses` 编排;每个 scheduler 内部先 `init_model_worker` 建 `ModelRunner`,再进事件循环。
4. KV 容量通过显存 profiling 自动推算,不是手填。
5. `ServerArgs` 是所有配置的中枢,也是设备适配的注入点之一。
