# 05 · 模型层与如何新增模型

> 本篇讲清 `models/` 与 `layers/` 的组织方式、模型文件的固定写法、权重加载机制,
> 并给出一份「新增模型」的实操清单。第三方适配时,模型层往往是改动量最大的地方之一。

---

## 1. 模型层的设计哲学

SGLang 的模型定义**不是**普通的 HuggingFace `transformers` 代码复制粘贴,而是一套「为服务而写」的约定:

1. **用服务专用积木**:`QKVParallelLinear`、`RowParallelLinear`、`RadixAttention`、`get_rope` 等,自带 TP 切分与 KV 池写入能力;
2. **无状态前向**:所有批信息通过 `forward_batch: ForwardBatch` 传入,模型不持有任何请求级状态;
3. **显式权重加载**:每个模型实现 `load_weights()`,把 HF checkpoint 的名字映射到融合后的参数(qkv 融合、gate/up 融合)并做 TP 分片;
4. **注册靠 `EntryClass`**:不需要装饰器,文件末尾声明入口类即可被发现。

---

## 2. 模型注册与发现(`models/registry.py`)

- 模块级单例 `_ModelRegistry` 在导入时执行 `ModelRegistry.register("sglang.srt.models")`。
- `import_model_classes()` 遍历 `sglang.srt.models` 包下所有模块并导入,收集每个模块的 **`EntryClass`** 属性——可以是单个类,也可以是**类列表**;建立 `类名 → 类` 的映射。
- 运行时用 HF config 的 `architectures`(如 `LlamaForCausalLM`)查表;查不到会回退到 `TransformersForCausalLM`(transformers 通用后端)。
- 第三方可以把自己的模型包放进独立 Python 包,并设置环境变量 `SGLANG_EXTERNAL_MODEL_PACKAGE`,实现**免改主仓**注册。

以 `llama.py` 结尾为例:

```924:928:python/sglang/srt/models/llama.py
EntryClass = [
    LlamaForCausalLM,
    Phi3ForCausalLM,
    InternLM3ForCausalLM,
    IQuestCoderForCausalLM,
]
```

## 3. 解剖一个标准模型文件(以 LLaMA 为例)

`models/llama.py` 的类结构是绝大多数模型的模板:

```
LlamaForCausalLM          # 顶层:embed → backbone → lm_head → logprob
└── LlamaModel            # backbone:逐层跑 LlamaDecoderLayer,最后 norm
    └── LlamaDecoderLayer # input_layernorm → attn → post_attention_layernorm → mlp
        ├── LlamaAttention  # qkv_proj + rotary + RadixAttention + o_proj
        └── LlamaMLP        # gate_up_proj(MergedColumnParallelLinear)+ down_proj
```

### 3.1 Attention 层的标准写法

```184:217:python/sglang/srt/models/llama.py
        self.qkv_proj = QKVParallelLinear(
            hidden_size,
            self.head_dim,
            self.total_num_heads,
            self.total_num_kv_heads,
            bias=bias,
            quant_config=quant_config,
            prefix=add_prefix("qkv_proj", prefix),
        )
        self.o_proj = RowParallelLinear(
            self.total_num_heads * self.head_dim,
            hidden_size,
            bias=bias,
            quant_config=quant_config,
            prefix=add_prefix("o_proj", prefix),
        )

        self.rotary_emb = get_rope(...)
        self.attn = RadixAttention(
            self.num_heads,
            self.head_dim,
            self.scaling,
            num_kv_heads=self.num_kv_heads,
            layer_id=layer_id,
            ...
        )
```

前向约定:

```240:264:python/sglang/srt/models/llama.py
    def forward(
        self,
        positions: torch.Tensor,
        hidden_states: torch.Tensor,
        forward_batch: ForwardBatch,
    ) -> torch.Tensor:
        ...
        q, k, v = self.forward_prepare_native(positions, hidden_states)
        attn_output = self.attn(q, k, v, forward_batch)
        output, _ = self.o_proj(attn_output)
        return output
```

要点:

- **输入输出都是「摊平」的**:`hidden_states` 形状 `[total_tokens, hidden]`(整个 batch 所有 token 拼一起),不做 padding;
- `qkv_proj` 一次算出 q/k/v(融合 GEMM);`rotary_emb(positions, q, k)` 施加 RoPE;
- `self.attn(q, k, v, forward_batch)` 即 `RadixAttention`,它内部完成:**写 KV 池(`out_cache_loc`)→ 按 forward_mode 分发到当前 attention backend → 返回 `[total_tokens, num_heads*head_dim]`**;
- `o_proj` 是 RowParallelLinear,内部做 TP all-reduce。

> 注意 llama.py 里还有一段 `forward_prepare_npu`:NPU 上用了融合的 split+rmsnorm+rope 算子。这是「同一模型、多设备快速路径」的典型模式。

### 3.2 RadixAttention 是模型与后端的唯一接口


模型作者只管构造它并调用;**具体用哪个 kernel、怎么写 KV、怎么组页表,全由运行时选定的 attention backend 决定**(见文档 06)。MLA 模型传 `v_head_dim`(latent 维度),SWA 模型传 `sliding_window_size`。

### 3.3 DecoderLayer 与 backbone

`LlamaDecoderLayer.forward` 是带**融合残差 layernorm** 的结构(注意签名里 `residual` 是显式传入/返回的):

```python
def forward(self, positions, hidden_states, forward_batch, residual):
    if residual is None:                      # 第一层
        residual = hidden_states
        hidden_states = self.input_layernorm(hidden_states)
    else:
        # 融合算子:一次 kernel 完成 residual 相加 + layernorm
        hidden_states, residual = self.input_layernorm(hidden_states, residual)

    hidden_states = self.self_attn(positions, hidden_states, forward_batch)

    hidden_states, residual = self.post_attention_layernorm(hidden_states, residual)
    hidden_states = self.mlp(hidden_states)
    return hidden_states, residual            # 残差一路外传,不在层内相加
```

两个要点:① `layernorm(x, residual)` 双参形态是 vLLM 系的融合算子(add + norm 一个 kernel),比「先加再 norm」省一次读写;② 残差不在层内相加,而是随返回值传递,由 backbone 统一收尾——移植模型时**不要**把它写成朴素的 `residual + hidden` 双语句版本,会丢掉融合收益且与权重语义不符。

`LlamaModel.forward` 负责 embed、逐层循环(首层传 `residual=None`),末尾用 `norm(hidden, residual)` 合并最后一路残差,再交给 `LlamaForCausalLM` 的 `LogitsProcessor`(文档 08)。

## 4. 权重加载:load_weights 的艺术

HF checkpoint 里 q/k/v 是三个矩阵,SGLang 里是一个 `qkv_proj.weight`;gate/up 同理。`load_weights` 要完成**名字映射 + 融合 + TP 切片**。

```665:672:python/sglang/srt/models/llama.py
        stacked_params_mapping = [
            # (param_name, weight_name, shard_id)
            ("qkv_proj", "q_proj", "q"),
            ("qkv_proj", "k_proj", "k"),
            ("qkv_proj", "v_proj", "v"),
            ("gate_up_proj", "gate_proj", "gate"),
            ("gate_up_proj", "up_proj", "up"),
        ]
```

流程:

1. 迭代 `weights`(name → tensor 生成器,支持 safetensors 流式读取);
2. 遇到 `q_proj/k_proj/v_proj` 按 shard_id 写入 `qkv_proj` 对应区段;`weight_loader` 会按 TP rank 只拷贝自己那份切片;
3. 量化模型(AWQ/GPTQ/FP8…)走对应的 quant config 的 loader;
4. 返回未匹配的参数名集合(用于诊断)。

加载器本身由 `model_loader/` 提供:`get_model_loader()` 默认返回 `DefaultModelLoader`(先空模型、再填权重),还有 sharded/dummy/远程等变体。

## 5. ModelRunner:模型的驾驶舱

`model_executor/model_runner.py` 的 `ModelRunner` 把「配置 → 模型 → 前向」串起来:

- `initialize()`:解析 config、`load_model()`、初始化 TP 通信、profile 显存、`alloc_memory_pool()`、初始化 attention backend、(可选)捕获 CUDA Graph;
- `forward(forward_batch)`:
  - decode 且满足条件 → **CUDA Graph replay**(整段 decode 前向一次图回放);
  - 否则 eager 路径(`EagerRunner` 按 extend/decode/idle 分发);
- 持有 `kv_cache`、`attn_backend`、`ParallelState`(tp/pp 信息)等。

对适配者来说,ModelRunner 是「设备假设」最集中的地方之一(显存测量、graph 捕获、stream 使用),务必通读。

### 5.1 CUDA Graph:decode 阶段的核心优化

这个机制在文档 02/06/07 里被反复引用,这里讲透。

**为什么 decode 需要它。** decode 阶段每步只算 1 个 token,单步 GPU 计算量极小(几十到几百微秒),但一次前向要 launch 成百上千个 kernel。Python 解释开销 + kernel launch 开销**远超实际计算**,GPU 大部分时间在等 CPU 喂指令。CUDA Graph 把整段前向的 kernel 序列**一次性录制**成一张图,之后每步只需一次 `replay()` 调用,把 CPU 侧开销从「上千次 launch」压成「一次提交」。小 batch decode 上这通常带来 **1.5~2 倍以上**的吞吐提升。prefill 阶段计算量大、launch 开销占比低,收益小得多(所以默认只对 decode 捕获)。

**核心矛盾:图是静态的,batch 是动态的。** CUDA Graph 要求每次 replay 的**张量地址和形状完全一致**,但真实负载里 batch size 每步都在变。SGLang 用两招解决:

1. **固定缓冲区**:捕获前预分配一批「图专用」输入输出张量(`self.buffers`),replay 前把真实数据 `copy_` 进去。图里记录的永远是这些固定地址。
2. **分桶捕获 + padding 到桶**:预先对一组离散的 batch size 各捕一张图,运行时把真实 bs **向上取整**到最近的桶。

分桶列表的构建在 `get_batch_sizes_to_capture`:

```88:91:python/sglang/srt/model_executor/runner/base_cuda_graph_runner.py
    # Model input token count = bs * alignment_width; must be a multiple of attn_tp_size.
    capture_bs = [bs for bs in capture_bs if bs * alignment_width % mul_base == 0]
    capture_bs = [bs for bs in capture_bs if bs <= num_max_requests]
    capture_bs = list(sorted(set(capture_bs)))
```

要点:候选桶来自 `--cuda-graph-bs-decode`(默认一组从 1 开始的稀疏序列),然后被两个约束过滤——**必须满足 attention TP/CP 的对齐要求**(token 数是 `attn_tp_size` 的倍数),且**不超过 `req_to_token_pool.size`**。若 `--max-running-requests` 很小导致所有默认桶都被滤掉,代码会补进 `num_max_requests` 保证至少有一张图。

运行时的 padding 就一行:

```1084:1085:python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py
                bs = self._pad_to_bucket(raw_bs, self.capture_bs)
            padded_num_tokens = bs * self.captured_req_width
```

**padding 的代价**:真实 bs=17 而桶是 `[16, 24]` 时,会按 24 跑图,7 个槽位算的是无效数据然后丢弃。所以桶设得太稀会浪费算力,太密则捕获耗时长、显存占用高(每张图都要占一份工作区)。这就是 `--cuda-graph-bs-decode` 的调优空间。

**哪些情况必须退回 eager。** `can_run_graph()` 逐项否决,常见原因:

- batch 里有 extend/prefill(除非启用了 prefill graph 或投机解码的特定模式);
- 真实 bs 超过 `max_bs`(最大的桶);
- 使用了动态的 per-request 特性,比如 `forward_batch.replace_embeds is not None`(逐请求覆盖 token embedding,地址无法固定);
- attention backend 声明本 batch 的 metadata 无法用图内路径表达。

**对适配者最关键的一点**:CUDA Graph 与 attention backend 是**强耦合**的。图内不能有任何 CPU-GPU 同步、动态 shape、host 侧分支——而 attention 的 metadata(seq_lens、block table 等)天然依赖 batch 内容。这正是文档 06 里 `init_forward_metadata_capture_cuda_graph` / `replay_cuda_graph` 这组接口存在的原因:**捕获期**建立指向固定缓冲区的 metadata,**replay 期**只允许原地更新这些缓冲区的内容,绝不重新分配。新硬件后端若一时无法满足这些约束,应让 `support_cuda_graph()` 返回 False 先跑通 eager 正确性,再逐步开图(见文档 07 的 M0→M4 路线)。

## 6. 实操:新增一个模型的步骤清单

1. **找最近的亲戚**:新模型多半是 LLaMA/Qwen2/Mistral/DSV2 的变体。直接复制最像的文件改名。
2. **对齐 HF config**:确认 `architectures` 名字、`config.json` 字段(hidden size、头数、rope 类型、tie embedding 等)。
3. **改结构差异**:MLP 变体、滑动窗口、共享 norm、交错层等——只动结构,保持积木不变。
4. **写 `load_weights`**:先跑通 `--load-format dummy` 验证结构,再加载真实权重对比。
5. **声明 `EntryClass`**,文件放进 `models/`。
6. **正确性验证**:
   - 单卡小模型 `generate` 对比 HF transformers 输出;
   - `test/registered/` 里仿写一个模型测试(参考 `write-sglang-test` skill);
   - 跑 `gsm8k` / `mmlu` 基准(`python -m sglang.bench_serving` / `lm_eval`)。
7. **性能验证**:开 CUDA Graph、对比 prefill/decode 吞吐;必要时加量化支持。
8. **多模态模型**另需实现 processor 与 embedding 注入(`multimodal/`),复杂度高一档。

## 7. 本篇要点回顾

1. 模型文件 = 「HF 结构 + 服务专用积木」;积木(ParallelLinear/RadixAttention/get_rope)自带 TP 与 KV 池语义。
2. `EntryClass` 声明即注册;`SGLANG_EXTERNAL_MODEL_PACKAGE` 支持外部模型包。
3. 前向约定:`[total_tokens, hidden]` 摊平输入 + `ForwardBatch` 上下文;模型无状态。
4. `load_weights` 负责名字映射、参数融合与 TP 切片,是新增模型最容易出错的地方。
5. ModelRunner 负责加载、显存 profile、graph 捕获与前向分发——设备适配的重灾区。
